# Tedate

> 本文译自英文版，以英文版为准。

一个面向 Claude Code 和 Codex 的产品判断 skill，帮你决定做什么、改什么，以及结果行不行。

- **选好下一步。** 把一个想法、一个功能需求，或者“总觉得哪里不对”，变成一条明确的建议。
- **给工作定方向。** 把设计或工程工作整理成范围明确的任务，带上你的目标和已经确定的决定。
- **评判结果。** 检查这项工作有没有解决最初的问题、还有什么要处理、什么时候该停。

Agent 能把功能做出来。但它该不该做、体验行不行、什么时候该停，仍然要你来判断。这些要求你也可以直接告诉 agent。Tedate 把它们写成了使用它时的默认工作方式。

**产品由你做主，构建交给你的 agent。**

*Tedate 的名字来自“手立て”（てだて），日语里指做成一件事的办法、手段。*

## 再改一轮也没用的时候

你让它重新设计。页面更干净了，但用户想做的事，页面还是没帮上忙。

你又加了一个功能。它能用，可你更不确定这个产品到底是做什么的了。

Agent 报告测试全过了。你还是不知道最初的问题解决了没有。

Tedate 就是为这些时刻写的。它帮你把判断说清楚：这里什么最重要，什么该改，什么该保留，什么证据才够。

有时建议是去做。有时是先查清一个不确定的点、缩小范围，或者先别动。

## 勾选框不等于下一步

作者有一次用 Tedate 检查一个家庭健康信息页，因为它在看诊时用起来很别扭。

读了代码之后，agent 发现一处可能的缺口：页面让人勾选**“我知道下一步”，却没有记录下一步具体是什么。**关闭看诊视图后，勾选状态也都消失了。

建议的下一步因此变了。先别改版：回放一次最近不顺的看诊，找到页面从哪一刻起帮不上忙，是准备问题、记录回答，还是知道之后要做什么。

这就是 Tedate 想支持的那种判断：在要求再来一版之前，先找到更值得解决的问题。

## 带一个你正卡住的决定来

- **要做的太多：** “这些想法里，现在哪个值得投入？”
- **又一轮不满意的改版：** “我试过两版了，到底还有什么不对？”
- **在几个方向里选：** “哪个方案更符合我们想做的事？”
- **Agent 说做完了：** “有什么能说明最初的问题真的解决了？”

你会得到一个建议，以及贴合你情况的理由。除了简单的问题，回答还会说明哪些内容没有检查、下一步由谁做什么；涉及较大的决定时，也会写明什么结果会改变这个建议。

不需要先写好完整的需求。举一个你实际遇到的、卡住的例子，就可以开始。

## 让目标贯穿整个构建

写代码有个原则：不要重复自己（don't repeat yourself）。skill 也一样。访谈、设计、工程方面已经有不少好的专业 skill，Tedate 选择与它们配合，不再重复实现。它可以独立帮你做判断；需要更深入的工作时，会交给合适的专业 skill。

用访谈类 skill 梳理想法，用设计类 skill 打磨体验，用工程类 skill 去构建。每次交接时，Tedate 都会带上产品目标和已接受的决定，再对照最初的意图检查结果。

![流程图：Tedate 把你的目标和已接受的决定带入一个聚焦的任务，交给专业 skill（访谈、设计或工程）；结果回来后对照最初目标检查。解决了就由你决定下一步；没解决就指出缺什么，再来一轮。](assets/tedate-handoff.png)

举个示意例子，“把这个页面做得更好”可以变成一个具体的设计任务：让食谱标题成为明确的视觉重点，沿用已有的卡片间距。改完后，再到同一个页面检查这些问题，同时判断整体效果。

简单的问题直接回答即可。其他 skill 都是可选的；没有它们，Tedate 仍会给出建议和一个可执行的任务。

工作跨越多次会话时，Tedate 会在你的项目里用一份简短的记录保存已接受的决定，只有你同意才会写。它不会让你的 agent 自动拥有跨会话记忆，其他 skill 也可能不遵循交接要求。

装的 skill 规则互相拉扯时（比如一个要求先写测试，另一个说先上线再补测试），Tedate 会根据你已接受的决定提出处理方案，并把它带进交接任务。你还没定过的，它给出建议，由你确认。换了 skill，你已经确认过的方向会写进交接任务。

## 安装

### Claude Code（插件方式）

```bash
claude plugin marketplace add fengyu20/tedate
claude plugin install tedate@tedate
```

在新会话里输入（插件里的 skill 会带上插件名作为前缀）：

```text
/tedate:tedate 这个页面看着不对,但我说不出哪里不对。
```

当你的请求符合它的描述时，它也可能自动触发。

### 或者复制 skill 文件夹（Claude Code 或 Codex）

克隆本仓库（或下载 zip），然后把 `skills/tedate` 复制到你的 skills 目录。文件夹必须仍叫 `tedate`。

```bash
git clone https://github.com/fengyu20/tedate.git
cd tedate
```

Claude Code：

```bash
mkdir -p ~/.claude/skills
cp -R skills/tedate ~/.claude/skills/
```

然后输入 `/tedate 这个页面看着不对,但我说不出哪里不对。`

Codex：

```bash
mkdir -p ~/.agents/skills
cp -R skills/tedate ~/.agents/skills/
```

然后输入 `$tedate 这个页面看着不对,但我说不出哪里不对。` 如果没有出现，重启 Codex。

Tedate 开头会先说明自己处于哪种模式：`advise`、`delegate` 或 `execute`。这是它被用上的一个迹象；更重要的是，它的建议能否帮你做出实际的决定。

更新插件：运行 `claude plugin update tedate@tedate`；卸载：`claude plugin uninstall tedate@tedate`。如果你是复制文件夹安装的，先 pull 仓库，再把 `skills/tedate` 重新复制一遍；要卸载，删掉 skills 目录里的 `tedate` 文件夹。

## 使用前须知

- **它的判断可能出错。** 要求给出来源和日期，并不能保证事实本身是对的。拍板的是你。
- **交接取决于你的环境。** 其他 skill 是可选的，它们是否遵循交接，取决于那个 skill 和你的环境。[为什么要交接](#让目标贯穿整个构建)。Tedate 和已有的产品、设计类 skill（比如 [Impeccable](https://github.com/pbakaus/impeccable)、[gstack](https://github.com/garrytan/gstack)、各种 PM skill 包）有重叠。 Tedate 只会交给你已安装的 skill，是否安装由你决定。
- **它读什么、写什么。** 它会读你的项目文件、git 历史和你指向的分析数据，也可能让你的 agent 查询公开资料。只有你同意时才会写决定记录。它不带任何脚本，自己也不会把数据发到任何地方；要把你的想法发给第三方服务，需要你再次同意。
- **范围是产品判断。** 它不管发布流程、版本号或合并冲突，不执行针对具体渠道的营销活动，也不产出 PRD 或路线图。
- **花钱、发布等操作仍由你把关。** 它被要求在没有你明确同意时不花钱、不发布、不部署，并且从不替你联系任何人。这些是写在提示里的规则，不是技术上的保障。

## 来由

我在做 [PYOKO](https://pyoko.jp/?utm_source=github&utm_campaign=tedate-readme)，一个东京博物馆通票「ぐるっとパス」的非官方指南，大部分是和 coding agent 一起做的。Agent 能把我提出的要求做出来，但我该提什么要求，仍然是个问题。有时我放手让它自己改页面，结果反而更难用了。我觉得不对劲，却说不清该怎么改。有时任务已经报告完成，最初的问题却还在。网站上线后，来的人很少，我又得想：先让谁知道这个网站，怎么判断推广有没有用？

于是，我开始把这些经历里学到的东西记下来：改页面前，先说清楚是给谁用的；判断做没做完，要看什么证据；修改时，要保留哪些已经确定的决定；交付前，再回头看看最初的问题解决了没有。大部分规则都来自实际遇到的问题，有的发生在 PYOKO 上，有的发生在其他小项目上。

这些笔记慢慢整理成了 Tedate。我希望它能帮你把“感觉不对”说清楚，找到问题，再想出下一步该做什么。最后由你来决定。
