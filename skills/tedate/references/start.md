# Starting from an idea

Check: Is the user task written (Run step 2)? Which single unknown most affects the next step? A missing preference: ask. A missing fact: check a source. Missing evidence about how people use it: pick the cheapest check that answers it (existing records, watching real use, or a small sample). Then choose how deep to go:
- Idea still vague: if facts are missing, first write which public sources you will check (`reach.md`, Listen) and check at least one; then hand it to an interview skill (for example grill-me), then continue. Tell the interview skill to stop splitting a distinction (for example "would use it weekly" versus "would use it once") unless the answer would change the scope now.
- Clear, but unsure it is worth doing: hand it to a challenge skill (for example the-fool, for a pre-mortem or devil's advocate), or run the checks below yourself.
- Clear enough: when the next step depends on other people's needs, listen first (`reach.md`, Listen); for a tool only the owner will use, start from the owner's own process and real samples. Ask: Who has this problem now? How do they solve it today, where does that fall short, and what would make them switch (from what they have done, not a guess)?

When the product depends on outside content or data, check real items before judging supply: sample at least 3 to 5 actual listings, offers or pages and note what is missing for a user to act on.

Before each further question, ask: would the answer change the next action? If not, stop asking and check a real source, build a small sample or give the recommendation. One real past behaviour is enough to justify a cheap exploration; it does not show general demand.

Add. A full start, meaning a plan for the first real test, needs every line; a check on whether the idea is worth exploring gets the conclusion and one reason (Run step 4):
- the user task;
- the smallest result that serves it and who builds it; why the intended user would pick it over how they do it today, which part of that benefit the first version must show, and what it gives up. When different readings of the request would change the first version, take the user's stated motivation as the guide and label inferred motivations as hypotheses;
- where the first real users come from: name the channel and how the owner would reach them (a line without a channel is unfinished, and strangers count; a friend's politeness does not). For a tool only the owner will use, the owner is the first user and no channel is needed;
- a success signal written before you start, with when you will look. Record steps of different strength separately (looked, chose, committed, completed). Numbers and deadlines follow the proposal rule in SKILL.md ("Kinds of statement"), even if the basis is only "a guess, to be adjusted after the first sample";
- up to three assumptions that could sink the idea, the most fatal one and the cheapest way to test it (the hardest real cases first is one way). For a content product, include whether valuable items can be found, explained and kept current;
- the stop condition (situation 8).

When the answer returns, say how it changes the next step.
Missing data or access: continue the work that does not depend on it. Use a substitute when it serves the original task or tests a named hypothesis, and state what it cannot prove.
